## 后端流程介绍

IDV-ASAS 的后端流程如下：

第 0 步：配置 API 接口。

接受前端接收到的配置信息，并将用户输入的配置信息存入配置文档中，API-key 可明文保存但需要提示用户风险。

配置需要包含模型选择、最大 Token 数限制、温度参数等。

API 的兼容性可参考 ../test/USAGE.md 中的 API 接口部分。

第 1 步：输入全局用户需求。

接受前端接收的全局用户需求，将全局用户需求保存，这一部分将会一直使用。若该局被保存历史，则历史中也需要记录全局需求，避免让用户二次输入。

第 2 步：选择当局地图。

接受前端接收到的地图信息并保存。

第 3 步：选择当局角色。

接受前端接收的用户选择的角色信息并保存。

第 4 步：输入当局用户需求。

接受前端接收的当局用户需求。这一部分和全局用户需求共同构成了用户需求。

第 5 步：调用模型进行分析。

让模型阅读 ../DICTIONARY.md 弄清楚角色对应的数据文件所在地址。

让模型阅读 ./README.md 和 ./characters/README.md 以及 ./maps/README.md 弄清第五人格游戏以及天赋选择、区域选择的模式。

给予模型本局地图对应的数据以及四名角色对应的数据并让它阅读。

让模型给予 2 到 3 套合理的天赋选择、区域选择，按推荐程度由高到低排列，这一部分的返回信息应当形如 “x 号选点：角色名：两个天赋” 以方便前端做处理（例如：2 号选点：佣兵：化险为夷、回光返照），注意这里只需要 “x 号选点” 而不需要俗称。（这里的要求与 ../test 中的处理方法不太一致，以这里为准。如果需要复用代码则注意修改）

除此之外，模型还需要生成该天赋、选点配置的描述与分析。这是一段不多于 100 字的流利的中文，重点介绍抗压与分工，不需要过多介绍推荐理由，在描述与分析时，禁止出现“x 号选点”这种编号说法，而应该采用俗称。

模型对于每个推荐需要且仅需要返回三个部分：方案编号（形如：“方案 1：”，共计 1 行），天赋选择与区域选择（共计 4 行），描述与分析（共计 1 行），不需要也不能有其余内容。

需要注意的是，每套推荐应是天赋与区域选择的独立组合，除非某一方存在唯一最优解。

这一过程需要支持打断，具体实现可参考 ../test/src/api.rs。

第 6 步：展示模型分析结果。

将模型分析的结果传递给前端，展示部分交由前端完成。

为防止出现多了前言、选点编号错误（超出最大编号、编号重复等）、描述与分析部分字数超限等问题，模型分析的结果需要进行一定的处理才能传递给前端。

处理方法：

- 若有多余的前言则删除多余的前言。

- 分析结果长度错误则直接截断至 100 字以内最后一个完整的句子并补充省略号。

- 若出现其余错误情况，包括模型返回不足/超过 4 名角色、角色名不存在、天赋名不存在、每角色天赋数不为 2、选点编号超出当前地图范围、返回了不存在的编号，则直接让模型重新生成并强调该问题。此过程最多重试三次，若依旧有问题，则强制退出并报告给用户：“您的模型与该项目不适配”。

第 7 步：等待用户结束对局并确认。

用户在前端确认完毕后，待前端发回确认指示。统计用户当局调用所消耗的 Token 用量以及费用并发送至前端，展示部分交由前端完成。

统计 Token 的方法可以参考 ../test/USAGE.md 。

第 8 步：询问用户是否开启下一对局。

接受前端发回的是否继续的信息，如果是则返回至第 2 步。

## 实现建议与指南

由于 ../DICTIONARY.md、./README.md、./characters/README.md 以及 ./maps/README.md 对于每局是共通的，因此可以提前交给用户在第 0 步中配置的模型阅读（当然不能只让模型阅读文件，需要有一定的 prompt 指示这些文件的用途和使用方法）。注意：这里的“阅读某文件”，指的是将文件内容注入到模型的 system prompt 中。

而到了分别的每局时，只需要提供给用户的模型对应的地图信息和角色信息即可。注意：这里的“阅读某文件”，指的是后端通过阅读 ../DICTIONARY.md，将对应的文件内容注入到模型的 prompt 中。

历史保存与导入应当交由后端实现。具体的实现方法可以参考 ../test/USAGE.md 与 ../test/README.md 中的方法与 ../test/src/history.rs 的具体实现。

## 实现要求

后端的实现必须使用 rust 完成。

注意：文中所有路径均是以该文件所在地为起始目录的。
